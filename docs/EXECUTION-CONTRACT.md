# Контракт исполнения и учёта состояния

**Статус:** требования к будущей реализации, не описание работающего кода. Применяется вместе с [ARCHITECTURE](ARCHITECTURE.md), [REVERT](REVERT.md) и [VERIFICATION](VERIFICATION.md).

## 1. План и идентичность

До изменения формируется разрешённый план: версия формата, версия playbook, SHA-256 содержимого пакета, версия AME, режим `live` / `injection` / `oobe`, build + UBR, редакция, архитектура, выбранные опции. Каждая запись содержит ID параметра, точную цель, исходное и ожидаемое состояния, способ проверки и отката.

Карточки параметров — описание намерения; YAML — декларация выполнения; план — разрешённые для конкретной среды действия. Валидатор должен сверять все три представления. Способ построения плана выбирается в v0.1; второй вручную поддерживаемый список ключей в скриптах не допускается.

Прогон получает `run_id`; снимок — `baseline_id`. Для live-системы фиксируется идентификатор установки, для пользовательских целей — SID. Для ISO фиксируются SHA-256 исходного файла, индекс редакции и архитектура образа. Baseline другого компьютера, пользователя, индекса или версии плана не используется автоматически.

## 2. Снимок до изменения

| Режим | Что должно быть снято | Ограничение |
|---|---|---|
| Live | все затронутые цели до первого действия | обязательный preflight |
| Injection | offline-цели до изменения смонтированного образа | OOBE не может получить это состояние задним числом |
| OOBE | live-цели до их изменения и ссылка на baseline injection | состояние уже изменённого образа не является исходным ISO |

В v0.1 используются live-изменения. До v0.3 требуется доказать получение и перенос baseline injection средствами процесса сборки, без запуска скриптов внутри injection-действий AME. Если это не реализовано, обратимые настройки остаются на OOBE. Подстановка «типичных значений чистой Windows» вместо фактического снимка запрещена. Вернуть настройки образа не означает отменить установку Windows или последствия setup; для полного возврата нужен внешний образ диска.

До первой записи проверяются возможность сохранить и прочитать снимок, свободное место, права, версия схемы и соответствие плану. Сбой любого условия блокирует изменения. Снимок сохраняется атомарно и не перезаписывается последующими apply; новый прогон хранит ссылку на исходный baseline. Новый baseline после успешного отката создаётся как отдельный цикл.

## 3. Контекст пользователя

До записи выясняются учётная запись процесса и целевой SID. `HKCU` процесса SYSTEM/администратора не считается `HKCU` будущего владельца. Для реестра фиксируются hive и 32/64-битное представление. Изменение Default User — отдельная цель, влияющая на будущие профили, и требует отдельного решения.

Если нужный профиль ещё не существует на OOBE, пользовательская настройка откладывается до явно предусмотренного запуска после входа либо исключается. Автозапуск ради этого не добавляется молча. Проверки S-10/S-14 должны охватывать владельца, второго пользователя и исполнителя с повышенными правами.

## 4. Журнал и остановка

Перед действием сохраняются намерение и prior-state, после — результат проверки. Состояния записи: `planned`, `started`, `applied`, `failed`, `skipped`, `unknown`. При выключении питания между записью и подтверждением остаётся `unknown`; повторный запуск сначала читает цель и сверяет её с исходным и ожидаемым состояниями.

При отказе preflight последующие изменения не выполняются. Ненулевой exit code PowerShell сам по себе не доказывает остановку AME: S-11 должен проверить, что контрольное действие после сбоя не было исполнено. До доказательства этого контракта изменяющий playbook не готов к первому прогону. При ошибке во время apply сохраняется частичный журнал, дальнейшие изменения прекращаются; автоматический массовый откат не запускается.

Фаза `90-report.yml` не является единственным местом сохранения результатов: аварийная сводка должна быть доступна, даже если эта фаза не достигнута. Повторный запуск запрещён при активном другом прогоне; способ блокировки и восстановления после сбоя определяется реализацией.

## 5. Откат и конфликты

Откат идёт по фактическому журналу в обратном порядке. Для каждой цели сравниваются три состояния:

| Текущее состояние | Действие |
|---|---|
| Совпадает с записанным playbook | восстановить baseline и проверить |
| Уже совпадает с baseline | записать отсутствие необходимости в изменении |
| Не совпадает ни с одним | `conflict`, не перезаписывать автоматически |
| Не читается либо baseline неполон | ошибка/неопределённость, без записи |

Удаляется только созданное этим прогоном и не изменённое позднее. Политики возвращаются к исходному значению; чужой ключ целиком не удаляется. Удаление службы не эквивалентно возврату типа запуска и не входит в начальный набор. Для Appx нужны отдельные доказательства восстановления регистрации, provisioning и данных.

## 6. Хранение и доверие

Предлагаемый корень артефактов — `%ProgramData%\WizardOS\runs\<run_id>\`, независимо от временной распаковки AME. Итоговый путь и ACL проверяются в реализации. Снимок и журнал доступны для записи только администраторам и SYSTEM. Файлы записываются через временный файл с атомарной заменой; исходный baseline остаётся неизменным.

Откат принимает данные по строгой версии схемы и allowlist целей. JSON/журнал не является источником команд для исполнения; произвольные пути и команды из него не запускаются. Хеш обнаруживает повреждение, но не доказывает подлинность при подмене вместе с файлом.

Локальные снимки могут содержать SID, пути профилей и конфигурацию. Перед публикацией отчёт редактируется и обезличивается; ключи восстановления BitLocker, токены и пароли в артефакты не включаются. Публичный HTML экранирует содержимое логов и значений.
