# Откат: стратегия и границы

## 1. Исходная проблема

У AME нет ни снапшота, ни undo, ни журнала изменений. Всё, что playbook сделал, откатывается только вручную. Сторонние проекты обычно прикладывают `.cmd`-файл, который «где-то удаляет то, что добавляли» — без снятого до применения состояния он принципиально не может быть точным.

Отсюда правило проекта: **откат проектируется до применения, а не после отказа.**

## 2. Два уровня отката

| Уровень | Что это | Когда |
|---|---|---|
| **Внешний** | снапшот ВМ или образ диска до прогона | всегда, обязательное условие прогона |
| **Внутренний** | откат средствами playbook по снятому prior-state | когда система жива, но конфигурация не устраивает |

Внешний уровень — единственная настоящая страховка. Внутренний — удобство и точность для обратимых изменений. Документ описывает внутренний.

## 3. Что снимается до применения

| Тип изменения | Prior-state |
|---|---|
| Значение реестра | существование, тип, данные; отдельно — состояние «значения не было» |
| Ключ реестра | существование; для удаления непустого ключа нужны все затронутые значения/подключи и права; без полного снимка удаление запрещено |
| Служба | тип запуска, текущее состояние, конфигурация восстановления, признак «хватало ли зависимостям» |
| Значение политики | существование, данные, источник (наш / внешний) |
| Appx | полный список пакетов и provisioned-пакетов |
| Запланированная задача | XML-представление до изменения |
| Файлы | хеш, путь и исходное содержимое каждого перезаписываемого/удаляемого файла с нужными метаданными; хеш не заменяет резервную копию |
| Состояние инвариантов | Secure Boot, TPM, VBS, гипервизор, драйверы, Store, Update |

Формат хранения: один структурированный файл рядом с отчётом, машиночитаемый, с версией формата. Путь фиксируется в отчёте и в [REVERT](REVERT.md) инструкции для человека.

Снимок на OOBE покрывает только последующие изменения. Для injection требуется отдельный снимок до изменения образа; ограничения и правила повторного запуска — [EXECUTION-CONTRACT](EXECUTION-CONTRACT.md). Исходный снимок не перезаписывается повторным apply.

## 4. Матрица обратимости

| Тип | Обратимо | Как | Ограничения |
|---|---|---|---|
| Значение реестра | да | вернуть тип и данные; удалить, если не было | если компонент сам перезаписал — результат иной |
| Ключ реестра | при полном снимке | восстановить затронутое поддерево; новый ключ удалить только если пуст | чужие значения и права сохраняются |
| Служба (тип запуска) | да | вернуть prior-state | если служба удалена — только восстановление из образа или переустановка компонента |
| Политика | да | вернуть исходный тип/данные; удалить только отсутствовавшее до apply значение | внешний источник политики не изменяется |
| Appx (удаление) | не доказано | проверять восстановление пакета, provisioning, регистрации и данных отдельно | Store/обновление не гарантируют точного возврата; без доказательства T4 |
| Appx (очистка кэша) | нет необходимости | кэш восстанавливается сам | — |
| Запланированная задача (удаление) | да | импорт XML | часть задач пересоздаётся компонентами — это не ошибка отката |
| Компонент ОС (`!systemPackage`) | **нет** | переустановка Windows или восстановление из образа | в v0.1 не используется |
| Доставленные файлы | условно | новые удалить, заменённые восстановить из копии | при последующем чужом изменении — конфликт, без перезаписи |
| Defender (при `DefenderDisabled`) | **нет** | переустановка Windows | не используется ([DECISIONS](DECISIONS.md) D-002) |

## 5. Порядок отката

Откатываются только подтверждённые изменения по журналу, в обратном фактическом порядке. При частичном прогоне план не заменяет журнал. Схема категорий ниже иллюстративна; `50-privacy.yml`, например, откатывается раньше `40-tasks.yml`:

```
отчёт и журнал (не откатываются)
  ↑
инварианты — проверяются, но не меняются
  ↑
запланированные задачи (импорт XML)
  ↑
Appx — только пометка «необратимо»
  ↑
службы (prior-state)
  ↑
реестр (значения и ключи, в обратном порядке записи)
  ↑
политики (восстановление исходных значений, на их месте в журнале)
  ↑
preflight-снимок
```

Перед возвратом сравниваются исходное, записанное playbook и текущее состояния. Если текущее изменилось позднее пользователем или Windows, фиксируется `conflict`, автоматическая перезапись запрещена. Импорт задачи не запускает её принудительно. Повторный откат не создаёт новых изменений.

## 6. Проверка отката (пункт приёмки)

1. Снапшот чистой ВМ → снимок состояния.
2. Применение playbook → верификация → отчёт.
3. Откат.
4. Снимок состояния → сравнение с исходным.
5. Ожидание: расхождения либо отсутствуют, либо полностью объяснены списком необратимого.

Если сравнение расходится и объяснения нет — это дефект отката, блокирующий релиз.

## 7. Что откат не чинит

1. Удалённые Appx-пакеты — только Store/обновление.
2. Удалённые компоненты ОС — только восстановление системы.
3. Изменения, которые компонент уже «подхватил» и перезаписал своим значением.
4. Миграцию профиля, если она произошла (например, конвертация учётной записи).
5. Последствия обновления Windows, пришедшего после прогона.

Это перечисляется в отчёте **до** применения, чтобы не было сюрпризов.

## 8. Инструкция для человека

В репозитории `REVERT` должен отвечать на три вопроса без чтения кода:

1. Где лежит preflight-снимок и как его найти.
2. Как запустить откат.
3. Что именно останется изменённым после отката и что с этим делать.

Документ-инструкция пишется на этапе v0.1 вместе со скриптом отката; здесь зафиксированы только требования к нему.
