# Журнал решений (ADR)

Формат: ID, статус, контекст, решение, последствия. Статусы: `proposed` (предложено, ждёт подтверждения), `accepted` (принято и действует), `rejected` (отклонено), `superseded` (заменено другим).

Правило: любое изменение в `Playbook/` обязано ссылаться на запись здесь. Если записи нет — изменение не вносится.

---

## D-001. Платформа: AME Playbook вместо собственного приложения

**Статус:** accepted

**Контекст.** Ранее рассматривался собственный toolkit (C#/GUI, брокер, адаптеры, журнал). Для задачи «свой набор изменений для чистой Windows 11 26H2 Pro» это означало бы разработку платформы исполнения с нуля.

**Решение.** Использовать AME Playbook как платформу исполнения. Своими силами делать контент, офлайн-валидатор, верификатор, отчёт и откат.

**Последствия.** Мы зависим от Beta-платформы и её формата. Зато нет собственного привилегированного брокера, своей модели распространения и своего формата — меньше поверхности ошибок. Требуется пиновать версию AME Wizard, на которой идёт тестирование.

## D-002. Defender не трогаем

**Статус:** accepted (подтверждено владельцем 2026-11-11, см. D-019)

**Контекст.** Единственный реальный способ «отключить Defender» средствами playbook — требование `DefenderDisabled`, при котором AME **удаляет Defender** из образа при сборке ISO. Политики реестра на свежей 26H2 не работают: включена Tamper Protection, и Windows игнорирует такие значения молча. Именно поэтому в известных playbook подобная опция была удалена — она создавала видимость работы.

**Решение.** Defender остаётся. Требование `DefenderDisabled` не используется. Опция «отключить Defender» в FeaturePages отсутствует.

**Последствия.** Минус десяток потенциальных «твиков» и весь связанный риск. Плюс — машина остаётся обновляемой и совместимой с приложениями, которые требуют включённой защиты. Отдельно фиксируем: молча не работающих опций в playbook быть не должно.

## D-003. BitLocker на ISO-пути отключается

**Статус:** accepted (подтверждено владельцем 2026-11-11)

**Контекст.** Windows 11 24H2+ включает автоматическое шифрование устройства на этапе setup. Ключ запечатан в TPM и привязан к измерениям прошивки. Обновление BIOS, переключение Secure Boot, сброс CMOS или очистка TPM приводят к запросу 48-значного ключа восстановления. На игровой/рабочей машине без сохранённого ключа это фактически кирпич. Ни один античит не требует шифрования диска; требуются Secure Boot и TPM 2.0, и они остаются включёнными.

**Решение.** `<ISO><DisableBitLocker>true</DisableBitLocker></ISO>`. Шифрование включается afterwards — осознанно, владельцем, с сохранённым ключом.

**Последствия.** Диск читаем при краже машины. Взамен машина всегда загружается после апдейта прошивки. Побочно: AME пишет в тот же `unattend` `BypassNRO=1`, снимая требование сети на OOBE.

## D-004. Требования setup не обходятся

**Статус:** accepted

**Контекст.** `<DisableHardwareRequirements>` позволяет поставить Windows на машину без TPM 2.0 и Secure Boot.

**Решение.** Не используется.

**Последствия.** Целевая конфигурация — реальный ПК с TPM 2.0 и Secure Boot; обход требований создал бы систему, несовместимую с античитами и корпоративными политиками. Чистая установка на неподдерживаемое железо — вне области проекта.

---

## D-005. VBS / Memory Integrity / виртуализация не трогаем

**Статус:** accepted; в части «ни одной опции» заменено D-022

**Контекст.** Отключение VBS и Memory Integrity — популярный «игровой» твик. На целевой машине одновременно живут WSL2, Docker Desktop и локальный AI.

**Решение.** Состояние VBS, Memory Integrity, гипервизора и `VirtualMachinePlatform` не меняется. Ни одной опции, которая их отключает, в playbook нет.

**Последствия.** Возможная потеря нескольких процентов в CPU-bound играх. Взамен работают WSL2, Docker, Windows Sandbox; часть античитов (Vanguard, FACEIT) не отказывается запускаться. Изменение состояния проверяется верификатором, чтобы отловить случайное вмешательство.

## D-006. Windows Update и Store остаются рабочими

**Статус:** accepted

**Контекст.** Отключение обновлений — источник неисправимых дыр; отключение Store ломает часть игр и установщиков.

**Решение.** Обе службы не отключаются. Максимум — управляемая пауза обновлений, если она вообще будет включена (отдельное решение).

**Последствия.** Машина остаётся обслуживаемой. Телеметрия и потребительский мусор вычищаются другими средствами, не через отключение обновлений.

## D-007. Appx: удалять только потребительский мусор

**Статус:** proposed

**Контекст.** Удаление Appx необратимо: вернуть можно через Store или обновление Windows. Некоторые приложения — часть инфраструктуры (Store, Xbox-стек, компоненты игр, средства разработки).

**Решение.** Удаляется только явный потребительский мусор, не связанный с играми, драйверами и разработкой. Полный список кандидатов фиксируется в [PARAMETERS](PARAMETERS.md) с обоснованием по каждому.

**Последствия.** Меньше «очистки», чем в агрессивных сборках, и это осознанно. Store и Xbox-стек сохраняются. Проводник и оболочка не затрагиваются.

## D-008. `!systemPackage` вне v0.1

**Статус:** accepted

**Контекст.** Удаление компонентов Windows — самый необратимый слой, напрямую влияет на обновляемость и совместимость.

**Решение.** В v0.1 не используется. Вводится по одному компоненту, отдельным релизом, с отдельным прогоном и записью в этом журнале.

**Последствия.** Первый релиз не конкурирует по «урезанности» с готовыми сборками. Это цена управляемости.

## D-009. Один профиль в v0.1

**Статус:** accepted

**Контекст.** Профили (Safe/Balanced/Extreme, Gaming/Developer) — это комбинаторика путей, каждый из которых надо прогнать на 26H2.

**Решение.** v0.1 — один фиксированный набор без FeaturePages. Профили вводятся в v0.4 после стабилизации контента.

**Последствия.** Нет гибкости на старте, но есть предсказуемое тестирование. Пользователь один и железо известно — профилизация сейчас не даёт ценности.

## D-010. Свой откат как обязательный артефакт

**Статус:** accepted

**Контекст.** У платформы нет штатного отката. Практика сторонних проектов — `.cmd`-файл «на удачу», потому что prior-state никто не снимал.

**Решение.** До первого изменения снимается prior-state по каждому параметру; откат выполняется отдельным артефактом в обратном порядке; проверка отката — пункт приёмки релиза. Что откатить нельзя — перечисляется в отчёте заранее, а не после.

**Последствия.** Половина работы приходится на учёт состояния, а не на «твики». Именно это отличает проект от набора скриптов. См. [REVERT](REVERT.md).

## D-011. Порог входа параметра: измеримость

**Статус:** proposed

**Контекст.** Заявления о приросте FPS в этом сегменте не проверяются.

**Решение.** Параметр с заявленным влиянием на производительность не попадает в набор без критерия проверки: что именно должно измениться и как это видно в отчёте. Параметры без измеримого эффекта остаются только если у них есть иное обоснование (приватность, удобство, освобождение места).

**Последствия.** Набор будет меньше, чем у конкурентов. Зато каждая строка объяснима.

## D-012. Публикация и `ProductCode`

**Статус:** proposed

**Контекст.** `ProductCode` и статус verified выдаёт AME после ревью; он же даёт кнопку с сайтом.

**Решение.** v0.1 — личный playbook без `ProductCode`, без `Git`, без публикации. Решение о публикации принимается после прохождения тестовой матрицы целиком.

**Последствия.** Нет онлайновых обновлений playbook. Распространение — вручную, файлом с контрольной суммой.

## D-013. Репозиторий и имя проекта

**Статус:** accepted

**Контекст.** Имя проекта и адрес репозитория определяют поле `Git` в `playbook.conf`, имена релизных артефактов, ссылки в документации и то, куда потом заливается `CHANGELOG`.

**Решение.** Проект называется **WindowsWizard**. Репозиторий — `https://github.com/OlehHavrilko/WindowsWizard`, public, ветка `main`. Локальная рабочая копия остаётся в каталоге `D:\Projects\codex\winoptimizer` и не переименовывается: имя каталога — не имя продукта.

**Последствия.**
1. Поле `Git` в `playbook.conf` заполняется этим URL при первом публичном релизе (связано с D-012; до этого момента update-check не включается).
2. Релизные артефакты именуются `WindowsWizard-<версия>.apbx` — заменено D-025: `WizardOS-<версия>.apbx`.
3. История репозитория: автосозданный коммит GitHub объединён с локальным. Правило «commit/push только по прямой команде владельца» заменено D-026.
4. Смена имени или адреса репозитория после первого публичного релиза недопустима без записи в этом журнале: на URL завязан `Git` в метаданных playbook.

## D-014. Позиционирование: доказуемость вместо урезанности

**Статус:** accepted (следует из D-019 и D-020)

**Контекст.** AtlasOS и ReviOS конкурируют глубиной урезания и обещанием производительности; прирост независимыми замерами не подтверждён, а проверки применения, отката по исходному состоянию и контроля дрейфа после обновлений нет ни у одного из них ([COMPETITORS](COMPETITORS.md)).

**Решение.** Проект конкурирует доказуемостью и обратимостью: предпросмотр изменений, отчёт о фактическом применении, откат, контроль дрейфа, замеры на машине пользователя. Целевая ниша — машина «игры + разработка + локальный AI». Перечень функций — [DIFFERENTIATORS](DIFFERENTIATORS.md) F-01…F-09.

**Последствия.** По числу удалённых компонентов проект заведомо уступает. Основной объём работы — инструменты вокруг контента, а не сам контент. Обещания производительности в описаниях запрещены: только числа из замеров.

## D-015. Линия Lab: смелые опции при трёх условиях

**Статус:** accepted (владелец 2026-11-11: опции обязательны)

**Контекст.** Строго консервативный набор не даёт того, ради чего пользователи выбирают конкурентов. Конкуренты же применяют необратимые изменения без возможности вернуть. Наличие отката и верификатора позволяет предложить такие изменения ответственно.

**Решение.** Ввести отдельный набор опций Lab, выключенных по умолчанию. Опция допускается только при трёх условиях одновременно: локальный бэкап изменяемого, проверенный прогоном откат без сети, замер или иное доказательство эффекта в отчёте. Кандидаты — [DIFFERENTIATORS](DIFFERENTIATORS.md) F-10a…F-10d. Запреты [SAFETY](SAFETY.md) §4 Lab не обходит.

**Последствия.** Требуется уточнить [PARAMETERS](PARAMETERS.md) §4: T4 «не включается» остаётся в силе, а кандидат Lab обязан доказать обратимость и перейти в T3 до включения. Каждая опция Lab — отдельный релиз и отдельный прогон; линия начинается не раньше закрытия v0.5. D-007 и D-008 для Lab пересматриваются по каждой опции отдельной записью.

## D-016. Собственный Toolbox

**Статус:** accepted (решение владельца 2026-11-11)

**Контекст.** D-001 отказывался от собственного приложения. Владелец определил, что нужен инструмент после установки: твики по выбору, драйверы, каталог программ.

**Решение.** Делается Toolbox ([TOOLBOX](TOOLBOX.md)). D-001 остаётся в силе в части платформы исполнения при установке: playbook применяет AME. Toolbox — интерфейс к тем же карточкам, журналу и откату; отдельного набора скриптов у него нет. Стек — C# и WinUI 3 поверх общего движка (D-023).

**Последствия.** Появляется собственный привилегированный код и канал его обновления — нужны подпись и проверка целостности. Объём работы растёт; Toolbox начинается после playbook v0.1.

## D-017. Пресет «Стандарт» включает Copilot, Recall и Edge

**Статус:** accepted (решение владельца 2026-11-11)

**Контекст.** В D-015 удаление Copilot / Recall и Edge было кандидатом линии Lab. Владелец относит их к стандартному набору наравне с телеметрией и рекламой.

**Решение.** Отключение телеметрии, рекламы, Copilot / Recall / AI-функций оболочки и удаление Edge с сохранением WebView2 входят в пресет «Стандарт». Требования D-015 к ним сохраняются: бэкап, проверенный откат, проверка результата.

**Последствия.** Эти изменения должны быть доказаны обратимыми раньше, чем планировалось, — до выхода пресета. WebView2 не удаляется никогда. Возврат компонентов обновлением Windows отслеживает Drift Guard (F-05).

## D-018. Драйверы устанавливаются из Toolbox

**Статус:** accepted (решение владельца 2026-11-11)

**Контекст.** После чистой установки пользователь вынужден ставить браузер и искать драйверы на сайтах производителей.

**Решение.** Toolbox определяет железо и устанавливает драйверы GPU (NVIDIA, AMD, Intel), чипсета и устройств без браузера ([TOOLBOX](TOOLBOX.md) §4). Источники — только серверы производителя и каталог Windows Update; файл проверяется по цифровой подписи. BIOS автоматически не обновляется.

**Последствия.** Официальных API у NVIDIA и AMD нет: способ получения версии может сломаться и требует проверки и запасного пути. Запрет [SAFETY](SAFETY.md) §4 на вмешательство в Driver Store уточняется: установка драйвера штатным установщиком производителя разрешена, ручная правка хранилища — нет.

## D-019. Обновляемость как главный принцип

**Статус:** accepted (решение владельца 2026-11-11)

**Контекст.** Отключённый Defender и заблокированные политиками обновления — причина, по которой пользователи избегают подобных playbook: обновить Windows потом трудно, а новая сборка ломает результат.

**Решение.** Defender не отключается и не удаляется; Windows Update не блокируется политиками. Проект обязан переживать свежие сборки: механизмы F-12a…F-12e ([DIFFERENTIATORS](DIFFERENTIATORS.md) §5). Этим владелец подтверждает D-002 и усиливает D-006.

**Последствия.** D-002 считается подтверждённым. Режим обновлений F-10c допускает только отсрочку обновлений функций, без запрета исправлений безопасности. Нужна инфраструктура ВМ для проверки новых сборок.

## D-020. Модель проекта: для себя, открыто, бесплатно

**Статус:** accepted (решение владельца 2026-11-11)

**Решение.** Проект делается в первую очередь для владельца; целевой пользователь — один человек, совмещающий игры, разработку и обычное использование. Репозиторий открытый. Платных функций не будет никогда; допустима только ссылка на добровольное пожертвование. Интерфейс — русский, украинский, английский. Публичный выпуск — возможен позже, отдельным решением (D-012).

**Последствия.** Приоритеты определяет эталонная машина ([REFERENCE-MACHINE](REFERENCE-MACHINE.md)). Уровень 2 адаптации к обновлениям (отчёты пользователей) откладывается до публичного выпуска.

## D-021. Целевая система

**Статус:** accepted (решение владельца 2026-11-11, выбор версии — по рекомендации)

**Контекст.** 24H2, 25H2 и 26H2 построены на одной платформе (сборки 26100 / 26200 / 26300); 26H2 ставится поверх 25H2 пакетом включения. У владельца установлена 26300.9818.

**Решение.** Windows 11 Pro x64, только чистая установка, сначала десктопы. Основная версия — 26H2; 25H2 и 24H2 поддерживаются тем же набором, насколько позволяет общая платформа, и проверяются вторыми. Ноутбуки, Home и работающие системы с данными — позже.

**Последствия.** Гейты `builds` пишутся на семейство `>=26100`, а не на одну сборку. Различия между версиями фиксирует манифест совместимости (F-12c).

## D-022. VBS, Memory Integrity и защиты CPU — опции Lab

**Статус:** accepted (решение владельца 2026-11-11); частично заменяет D-005

**Контекст.** D-005 запрещал любые опции отключения VBS. Владелец требует, чтобы все твики производительности были доступны как опции: части пользователей не нужны WSL2, Docker и античиты уровня ядра.

**Решение.** Отключение VBS / Memory Integrity и защит CPU доступно в Lab, выключено по умолчанию. Описание опции прямо называет, что перестаёт работать: Vanguard, FACEIT, WSL2, Docker, Sandbox. По умолчанию состояние не меняется — эта часть D-005 остаётся. Defender и Windows Update опцией не становятся (D-019).

**Последствия.** [SAFETY](SAFETY.md) §4 уточнён. Compat Contract (F-07) обязан после включения опции показать, какие сценарии потеряны.

## D-023. Порядок работ: движок, затем playbook, затем Toolbox

**Статус:** accepted (решение делегировано владельцем)

**Контекст.** Playbook и Toolbox должны применять одни и те же твики. Если написать их в YAML для AME, Toolbox придётся повторять логику; владелец выбрал для Toolbox C# и WinUI 3.

**Решение.** Сначала делается общий движок на .NET: каталог карточек твиков и консольная утилита с командами `plan`, `apply`, `verify`, `revert`. Playbook AME — тонкая обёртка, которая при установке вызывает движок с набором «ядро». Toolbox на WinUI 3 — интерфейс к тому же движку. Стек PowerShell + WPF из D-016 отменён.

**Последствия.** Движок исполняется только на живой системе: на ISO-пути все твики идут на этапе OOBE, а не injection; декларативные действия AME используются минимально. [ARCHITECTURE](ARCHITECTURE.md) §3 и [ROADMAP](ROADMAP.md) подлежат пересмотру под эту схему до начала реализации. Движок работает и без AME — запуск на уже установленной системе возможен.

## D-024. Состав твиков, обновления, драйверы, каталог, телеметрия

**Статус:** accepted (решение владельца 2026-11-11; пункты 2 и 3 делегированы)

**Решение.**

## D-027. Платформа движка: .NET 10, self-contained

**Статус:** accepted (архитектурное решение, делегировано владельцем)

**Контекст.** Движок (D-023) запускается на свежей Windows из AME и из Toolbox. На чистой Windows 11 есть только .NET Framework 4.8.1; современного .NET нет. Toolbox на WinUI 3 требует современного .NET.

**Решение.** Библиотека `WizardOS.Core` и CLI `wizardos.exe` — .NET 10 (LTS), `win-x64`. CLI публикуется self-contained в один файл с обрезкой. Toolbox ссылается на ту же библиотеку. Каталог карточек — YAML в `catalog/`, встраивается в сборку как ресурс.

**Почему не .NET Framework 4.8.1.** Нет зависимостей, но Toolbox пришлось бы делить код между двумя рантаймами, а обрезка и современные API WinRT недоступны.

**Последствия.** Размер `wizardos.exe` — десятки мегабайт; проверяется в v0.1. Сборка требует .NET 10 SDK; проверка на Windows — в CI (`windows-latest`). Устройство слоёв — [ARCHITECTURE](ARCHITECTURE.md) §3–5.

## D-030. UCPD не отключаем и не обходим; статус BlockedByOS

**Статус:** accepted (по реализации задачи владельца 2026-11-11; архитектурное решение в части статуса — на подтверждение)

**Контекст.** На Windows 11 24H2+ драйвер UCPD.sys (User Choice Protection Driver) закрывает запись и удаление ряда ключей, в т. ч. `HKLM\SOFTWARE\Policies\Microsoft\Dsh\AllowNewsAndInterests`. На ВМ после перезагрузки bareos получает `UnauthorizedAccess`, из PowerShell запись блокируется так же.

**Решение.**
1. UCPD не отключается и не обходится (ни остановкой службы/задачи UCPD, ни подменой процесса, ни переименованием исполняемого файла): это защита ОС, а обход противоречит принципу «только проверяемые, откатываемые изменения» ([SAFETY](SAFETY.md)).
2. Движок различает такой отказ: статус `BlockedByOS` (рядом с `Failed`). Условие: «доступ запрещён» при записи/удалении в ключе из списка `UcpdGuard.ProtectedKeys` и служба UCPD запущена (не читается — решает ключ).
3. `BlockedByOS` не даёт код выхода 1 в apply/revert/verify; verify показывает n/a с причиной; в отчёте и CLI — «заблокировано ОС (UCPD)». Пустой ключ, не удалённый при откате из-за UCPD, — предупреждение, статус `Reverted`.
4. Карточка, цель которой защищена UCPD, остаётся `proposed`, пока не найден и не проверен на ВМ способ, который UCPD не блокирует. Групповая политика через Registry.pol — гипотеза, не проверена.

**Последствия.** Список защищённых ключей — константа в коде, пополняется по фактам из отчётов. Тест каталога требует `proposed` для карточек с такими целями.

## D-031. Обход UCPD через локальную групповую политику (отменяет п. 1 D-030)

**Статус:** accepted (прямое указание владельца, 2026-11-11)

**Контекст.** После D-030 движок честно сообщал `BlockedByOS`, но сам обхода не делал. Владелец явно потребовал сделать обход («сделай обход все же»), сначала попросив изучить, как это решают другие проекты (AtlasOS, Meridian 26H2, Winhance, 0Ai-Windows-Hardening, WinDebloat). Вывод: AtlasOS отключает UCPD целиком; Winhance и 0Ai его не трогают и честно показывают блокировку (как D-030); ни один из изученных проектов не показал рабочего обхода через групповую политику — это наша гипотеза, не чужая практика.

**Решение.**
1. Отменяется часть п. 1 D-030 «не обходим»: при блокировке UCPD движок пробует записать значение через локальную групповую политику (`Registry.pol` в `%SystemRoot%\System32\GroupPolicy\Machine` или `User`, затем `gpupdate /force`). Это не снимает защиту ОС — пишет тем же путём, которым пишет сама Windows (gpsvc), и который UCPD не фильтрует. Реализация: `IPolicyWriter` / `PolicyRegistryWriter`, подключён в CLI всегда (в отличие от п. 2 — это не отключение защиты).
2. Если попытка через политику не удалась (gpupdate не применил значение), остаётся прежнее поведение D-030: `BlockedByOS`, код выхода не меняется.
3. Отключение самой службы/задачи UCPD (`sc config UCPD start=disabled` + задача `UCPD velocity`) — явный p1, оставлен как задел, не реализован в этом PR: он снимает защиту ОС целиком, а не пишет через штатный механизм, поэтому должен быть отдельным флагом CLI с подтверждением и отдельным решением, когда понадобится.
4. Карточка `shell.widgets` остаётся `proposed` до проверки обхода на ВМ (после перезагрузки, где ключ `Dsh` реально блокировался).

**Последствия.** Формат `Registry.pol` (PReg) реализован и протестирован как чистые функции (`PRegFile`), без Windows; сама запись и `gpupdate` проверяются только на ВМ. Если на ВМ `gpupdate` не применяет значение в `Dsh`, гипотеза не подтвердится, и остаётся только D-030.
