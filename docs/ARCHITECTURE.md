# Архитектура Bare OS: движок, playbook, Toolbox

Документ описывает механику платформы AME и то, как под неё устроен Bare OS. Схема работ — [DECISIONS](DECISIONS.md) D-023: общий движок, над ним две обёртки. Всё, что помечено «требует проверки», проверяется на ВМ (см. [TEST-MATRIX](TEST-MATRIX.md)).

## 1. Что такое `.apbx`

`.apbx` — это 7z-архив с паролем **`malte`**, содержащий плоскую структуру папки `Playbook`. Пароль не защита, а способ не давать антивирусам и браузерам сканировать содержимое.

```
Playbook/
├── playbook.conf          XML: метаданные, требования, FeaturePages, ISO/OOBE
├── Configuration/
│   ├── main.yml           точка входа: title + actions
│   └── Tasks/*.yml        файлы задач, подключаемые через !task
├── Executables/           то, что вызывается из !run / !cmd / !powerShell
├── Images/                иконки для <Software> и OOBE
└── playbook.png           256 px, иконка playbook в AME Wizard
```

Обязательный минимум для загрузки playbook — `playbook.conf` и `Configuration/main.yml`. Остальное появляется по мере необходимости.

## 2. Два этапа исполнения

Ключевая особенность платформы: одно и то же дерево YAML исполняется в двух разных средах.

| | **Injection** | **OOBE** |
|---|---|---|
| Где выполняется | offline, на машине, собирающей ISO; образ смонтирован | живая Windows после установки с этого ISO |
| Когда | в момент сборки образа | на первой загрузке, вместо штатного OOBE |
| Кто исполняет | AME Wizard | подменённый OOBE-шим AME |
| Что вносится в образ | реестр, файлы, кэш загрузок, правка/удаление служб | всё остальное |
| Что **нельзя** | `!cmd`, `!run`, `!powerShell`, `!taskKill`, `!appx`, `!systemPackage` | — |

Управление на уровне действия — двумя необязательными свойствами:

- `iso: true | false | only` — выполнять ли на injection;
- `oobe: true | false | only` — выполнять ли при первом запуске.

Нельзя считать неуказанное `oobe` равным `true`: при `iso: true/only` действие по умолчанию пропускается на OOBE. `oobe: only` и `iso: only` исключают обычный live-прогон. Загрузки и установка ПО имеют особую механику кэша. Таблица маршрутизации и источник — [SOURCES](SOURCES.md); поведение вложенных `!task` проверяется на закреплённой версии AME.

**Важно:** несовместимое с injection действие не «тихо пропускается», а ломает разбор playbook целиком. Поэтому все файлы задач проверяются офлайн-валидатором до упаковки (см. [BUILD](BUILD.md)).

### 2.1 Что это значит для нас

1. Injection — единственный этап, где изменения ложатся **в сам образ**. Это дешевле по времени первого запуска и надёжнее для служб: правка offline-реестра не конкурирует с работающими компонентами.
2. Всё «живое» — приложения, задачи, компоненты ОС — исполняется на OOBE, то есть на свежеустановленной системе, где ещё не завершились первые задачи обслуживания. Это окно повышенного риска.
3. На OOBE нельзя выполнять операции, требующие завершённой пользовательской сессии. Offline-перенос допускается только при наличии исходного состояния до injection; технической совместимости действия недостаточно.

### 2.2 Три режима и граница исходного состояния

Обычный live-прогон AME, injection и OOBE — три разных маршрута. v0.1 проверяет live-прогон; поддержка ISO появляется отдельно в v0.3.

`00-preflight.yml` на OOBE видит уже изменённый образ и не может снять состояние **до injection**. Поэтому до v0.3 изменения выполняются только после live-preflight. Для v0.3 нужен отдельный снимок offline-целей до injection, привязанный к SHA-256 ISO, индексу образа и плану. Если получить и безопасно перенести такой снимок нельзя, изменение остаётся на OOBE. Подробный контракт — [EXECUTION-CONTRACT](EXECUTION-CONTRACT.md).

## 3. Слои системы (D-023)

```
            каталог карточек твиков (catalog/*.yml)
                          │  встраивается при сборке
                          ▼
   ┌──────────────── движок Bare OS (.NET) ────────────────┐
   │ BareOS.Core: карточки, план, обработчики, снимок,    │
   │                журнал, проверка, откат, отчёт          │
   │ bareos.exe:  plan | apply | verify | revert | report │
   └──────────────▲─────────────────────────▲───────────────┘
                  │ вызов CLI               │ ссылка на Core
        AME Playbook (.apbx)          Toolbox (WinUI 3)
        установка: live / OOBE        после установки
```

| Слой | Что делает | Чего не делает |
|---|---|---|
| Каталог | описывает каждый твик карточкой ([PARAMETERS](PARAMETERS.md)): цель, класс устойчивости, гейт сборок, проверка, откат, пресет | не содержит кода |
| Движок | строит план под конкретную систему, снимает исходное состояние, применяет, проверяет, откатывает, пишет отчёт | не имеет GUI, не зависит от AME |
| Playbook | доставляет движок на систему и вызывает его с пресетом и опциями из FeaturePages | не содержит своих твиков (кроме случаев из §4.2) |
| Toolbox | интерфейс к движку на живой системе: пресеты, отдельные твики, откат, драйверы и программы | не применяет твики в обход движка |

Твик пишется один раз — в каталоге. Ни playbook, ни Toolbox не держат второго списка ключей ([EXECUTION-CONTRACT](EXECUTION-CONTRACT.md) §1).

## 4. Движок

### 4.1 Команды

| Команда | Вход | Результат | Меняет систему |
|---|---|---|---|
| `plan` | пресет, опции | план: что будет изменено, что пропущено и почему (сборка, класс устойчивости, конфликт) | нет |
| `apply` | план или пресет | снимок → изменения → проверка каждого; журнал прогона | да |
| `verify` | `run_id` или пресет | сверка текущего состояния с ожидаемым: `ok` / `drift` / `mismatch` / `missing-target` | нет |
| `revert` | `run_id` | возврат к снимку для обратимых целей; список необратимого | да |
| `report` | `run_id` | текстовый и (с v0.2) HTML-отчёт | нет |

Коды возврата: `0` — успех, `1` — ошибка проверки или частичное выполнение, `2` — отказ preflight (изменений нет). Playbook останавливается по ненулевому коду (S-11).

### 4.2 Обработчики

Каждое действие карточки исполняет обработчик с тремя операциями: прочитать текущее состояние, применить, проверить. Откат — запись прочитанного состояния обратно.

| Обработчик | Этап | Обратимость |
|---|---|---|
| `registry` (HKLM, HKU по SID, Default User) | v0.1 | полная |
| `service` — тип запуска из allowlist | v0.1 | полная |
| `task` — включить/выключить запланированную задачу | v0.1 | полная |
| `appx` — удалить пакет для пользователей и provisioned | v0.2 | частичная: переустановка из Store |
| `capability` / `feature` | после решения Q-04 | частичная |

Действия, которые движок выполнить не может (например, правка образа на injection), остаются декларативными действиями AME и обязаны иметь карточку в каталоге.

### 4.3 Хранение

Прогоны — `%ProgramData%\BareOS\runs\<run_id>\`: план, снимок (`baseline`), журнал, отчёт. Права — только администраторы и SYSTEM; запись атомарная; baseline не перезаписывается ([EXECUTION-CONTRACT](EXECUTION-CONTRACT.md) §2).

### 4.4 Платформа

Движок — .NET 10 (LTS), `win-x64`, публикация self-contained в один файл с обрезкой (trimming): на чистой Windows нет современного .NET, а ставить runtime ради одного запуска — лишняя зависимость. Toolbox ссылается на ту же библиотеку `BareOS.Core`. Решение — [DECISIONS](DECISIONS.md) D-027.

## 5. Порядок фаз playbook

Порядок объявления `!task` в `main.yml` — порядок исполнения. Все твики идут через движок, поэтому фаз мало.

| Фаза | Файл | Содержимое | Этап |
|---|---|---|---|
| 0 | `00-engine.yml` | копирование `bareos.exe` в `%ProgramData%\BareOS\bin\`, проверка подписи и SHA-256 | live / OOBE |
| 1 | `10-plan.yml` | `bareos plan --preset <пресет> --options <из FeaturePages>`; отказ — остановка | live / OOBE |
| 2 | `20-apply.yml` | `bareos apply --plan <план>` | live / OOBE |
| 3 | `30-ame.yml` | декларативные действия AME, которые движок не выполняет (если есть) | по карточке |
| 4 | `90-report.yml` | `bareos verify` + `bareos report` | live / OOBE |

Injection для твиков не используется (D-023): на OOBE движок снимает исходное состояние живой системы. Injection остаётся только для того, что AME делает сам: `<ISO><DisableBitLocker>` (D-003), кэш загрузок, подмена OOBE.

Внутри `apply` порядок задаёт движок: реестр → службы → задачи → Appx. Более разрушительные операции идут последними, чтобы удаление компонента не уносило уже настроенную цель и было видно в отчёте.

## 6. Адаптация к обновлениям

После обновления Windows Toolbox (или задача по расписанию, если пользователь согласился) вызывает `bareos verify`. Цели со статусом `drift` возвращаются в ожидаемое состояние только для класса устойчивости A; `missing-target` помечает твик несовместимым с новой сборкой и отключает его. Подробно — [DIFFERENTIATORS](DIFFERENTIATORS.md) §5.

## 7. Границы ответственности

| Bare OS делает | Bare OS не делает |
|---|---|
| меняет реестр, тип запуска некритичных служб, задачи, состав потребительских Appx | не модифицирует установочный образ как продукт (это делает AME Wizard) |
| снимает исходное состояние, проверяет результат, формирует отчёт | не заменяет резервное копирование и точку восстановления |
| откатывает обратимое и прямо называет необратимое | не гарантирует работу сторонних драйверов и обновлений Windows |
| сохраняет Defender, Windows Update, WSL2, Hyper-V (D-002, D-019) | не отключает защиту без опции Lab (D-022) |

## 8. Поток данных

```
оригинальный ISO Microsoft
        │
        ├── AME Wizard: injection
        │       ├── playbook.conf → SupportedBuilds / Requirements / ISO / OOBE
        │       ├── <ISO><DisableBitLocker>, кэш загрузок
        │       └── подмена OOBE + копия playbook в ProgramData\AME\OOBE\Playbook
        │
        ├── установка Windows с полученного носителя
        │
        └── AME OOBE: первая загрузка
                ├── FeaturePages → пресет и опции
                ├── bareos plan → apply → verify
                └── %ProgramData%\BareOS\runs\<run_id>\ → отчёт

живая система:  AME Wizard (тот же playbook)  или  Toolbox → bareos
```

Проверка обязательна: на свежей системе часть действий может молча не сработать (пример: политика отключения Defender при включённой Tamper Protection), поэтому постусловия проверяются отдельно от отсутствия ошибок.
