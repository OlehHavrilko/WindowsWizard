# Архитектура: как устроен AME Playbook

Документ описывает механику платформы и то, как под неё спроектирован наш playbook. Всё, что помечено «требует проверки», проверяется на ВМ (см. [TEST-MATRIX](TEST-MATRIX.md)).

## 1. Что такое `.apbx`

`.apbx` — это 7z-архив с паролем **`malte`**, содержащий плоскую структуру папки `Playbook`. Пароль не защита, а способ не давать антивирусам и браузерам сканировать содержимое.

```
Playbook/
├── playbook.conf          XML: метаданные, требования, FeaturePages, ISO/OOBE
├── Configuration/
│   ├── main.yml           точка входа: title + actions
│   └── Tasks/*.yml        файлы задач, подключаемые через !task
├── Executables/           то, что вызывается из !run / !cmd / !powerShell
├── Images/                иконки для <Software> и OOBE
└── playbook.png           256 px, иконка playbook в AME Wizard
```

Обязательный минимум для загрузки playbook — `playbook.conf` и `Configuration/main.yml`. Остальное появляется по мере необходимости.

## 2. Два этапа исполнения

Ключевая особенность платформы: одно и то же дерево YAML исполняется в двух разных средах.

| | **Injection** | **OOBE** |
|---|---|---|
| Где выполняется | offline, на машине, собирающей ISO; образ смонтирован | живая Windows после установки с этого ISO |
| Когда | в момент сборки образа | на первой загрузке, вместо штатного OOBE |
| Кто исполняет | AME Wizard | подменённый OOBE-шим AME |
| Что вносится в образ | реестр, файлы, кэш загрузок, правка/удаление служб | всё остальное |
| Что **нельзя** | `!cmd`, `!run`, `!powerShell`, `!taskKill`, `!appx`, `!systemPackage` | — |

Управление на уровне действия — двумя необязательными свойствами:

- `iso: true | false | only` — выполнять ли на injection;
- `oobe: true | false | only` — выполнять ли при первом запуске.

Нельзя считать неуказанное `oobe` равным `true`: при `iso: true/only` действие по умолчанию пропускается на OOBE. `oobe: only` и `iso: only` исключают обычный live-прогон. Загрузки и установка ПО имеют особую механику кэша. Таблица маршрутизации и источник — [SOURCES](SOURCES.md); поведение вложенных `!task` проверяется на закреплённой версии AME.

**Важно:** несовместимое с injection действие не «тихо пропускается», а ломает разбор playbook целиком. Поэтому все файлы задач проверяются офлайн-валидатором до упаковки (см. [BUILD](BUILD.md)).

### 2.1 Что это значит для нас

1. Injection — единственный этап, где изменения ложатся **в сам образ**. Это дешевле по времени первого запуска и надёжнее для служб: правка offline-реестра не конкурирует с работающими компонентами.
2. Всё «живое» — приложения, задачи, компоненты ОС — исполняется на OOBE, то есть на свежеустановленной системе, где ещё не завершились первые задачи обслуживания. Это окно повышенного риска.
3. На OOBE нельзя выполнять операции, требующие завершённой пользовательской сессии. Offline-перенос допускается только при наличии исходного состояния до injection; технической совместимости действия недостаточно.

### 2.2 Три режима и граница исходного состояния

Обычный live-прогон AME, injection и OOBE — три разных маршрута. v0.1 проверяет live-прогон; поддержка ISO появляется отдельно в v0.3.

`00-preflight.yml` на OOBE видит уже изменённый образ и не может снять состояние **до injection**. Поэтому до v0.3 изменения выполняются только после live-preflight. Для v0.3 нужен отдельный снимок offline-целей до injection, привязанный к SHA-256 ISO, индексу образа и плану. Если получить и безопасно перенести такой снимок нельзя, изменение остаётся на OOBE. Подробный контракт — [EXECUTION-CONTRACT](EXECUTION-CONTRACT.md).

## 3. Порядок фаз

Порядок объявления `!task` в `main.yml` — это и есть порядок исполнения. Изменить его в рантайме нельзя, поэтому порядок проектируется жёстко, с числовыми префиксами имён файлов.

| Фаза | Файл | Содержимое | Этап |
|---|---|---|---|
| 0 | `00-preflight.yml` | prior-state для последующих live/OOBE-изменений, проверки окружения, план | live / OOBE |
| 1 | `10-registry.yml` | параметры системы и пользователя | injection + OOBE |
| 2 | `20-services.yml` | тип запуска служб из allowlist; удаление не входит в начальный набор | live; injection после решения о снимке |
| 3 | `30-appx.yml` | удаление мусорных Appx, очистка кэшей | OOBE |
| 4 | `40-tasks.yml` | запланированные задачи: удаление/правка | OOBE |
| 5 | `50-privacy.yml` | телеметрия, реклама, потребительский мусор | injection + OOBE |
| 6 | `60-invariants.yml` | явное подтверждение того, что WSL2/Docker/Store/Xbox/безопасность не тронуты | OOBE |
| 7 | `90-report.yml` | манифест изменений, запуск верификатора | OOBE |

Логика порядка внутри каждого режима: исходное состояние → изменения → проверка. Фаза 6 не меняет систему. Отказ preflight должен останавливать последующие изменения; одного ненулевого exit code скрипта недостаточно без проверки реакции AME (S-11). Отчёт о частичном выполнении сохраняется и при сбое до фазы 90.

Почему приложения и компоненты удаляются после реестра и служб: удаление компонента может унести службу или ключ, которые уже настроены, и тогда итоговое состояние зависит от порядка. Более разрушительные операции идут последними, чтобы их эффект был виден в отчёте.

## 4. Границы ответственности

| Playbook делает | Playbook не делает |
|---|---|
| меняет параметры реестра, состав потребительских приложений, тип запуска некритичных служб, запланированные задачи, приватность | не модифицирует установочный образ как продукт (это делает AME Wizard) |
| снимает prior-state и формирует отчёт | не заменяет резервное копирование и точку восстановления |
| проверяет постусловия и инварианты | не гарантирует работу сторонних драйверов и обновлений Windows |
| сообщает, что откатить нельзя | не выполняет полный откат удалённых компонентов |

## 5. Соотношение с «собственным toolkit»

Ранее обсуждалась идея отдельного приложения на C# с GUI и брокером. Для текущей цели она избыточна: платформу исполнения даёт AME Wizard, а наша работа — контент, валидатор, верификатор и стратегия отката. Приложение имело бы смысл, только если требовался собственный формат playbook или собственная GUI-оболочка; сейчас это лишний слой и лишняя поверхность ошибок.

Из прежнего замысла в проекте остаются три идеи, перенесённые в документацию:

1. **Модель параметра** — каждый параметр описывается карточкой (см. [PARAMETERS](PARAMETERS.md)), а не просто строкой YAML.
2. **Уровни риска и согласие** — опасные блоки вынесены в отдельные опции и по умолчанию выключены (см. [SAFETY](SAFETY.md)).
3. **Доказательство вместо обещания** — верификатор и отчёт обязательны (см. [VERIFICATION](VERIFICATION.md)).

## 6. Поток данных

```
оригинальный ISO Microsoft
        │
        ├── AME Wizard: injection
        │       ├── playbook.conf → SupportedBuilds / Requirements / ISO / OOBE
        │       ├── actions с iso:true|only → образ
        │       ├── !download / !software → кэш в образе
        │       └── подмена OOBE + копия playbook в ProgramData\AME\OOBE\Playbook
        │
        ├── установка Windows с полученного носителя
        │
        └── AME OOBE: первая загрузка
                ├── опции FeaturePages → выбор пользователя
                ├── actions с oobe:true → живая система
                └── verify + report → артефакт проверки
```

Отчёт и верификация — не «приятное дополнение», а единственный способ узнать, что playbook реально применился. На свежей системе часть действий может молча не сработать (пример из практики: политика отключения Defender при включённой Tamper Protection), поэтому постусловия проверяются отдельно от факта отсутствия ошибок.
