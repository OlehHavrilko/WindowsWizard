# Сборка, валидация и релизы

## 1. Принцип

Нельзя собрать `.apbx` «вручную из папки»: платформа падает на разборе, если в YAML есть несовместимое действие или нарушены лимиты FeaturePages. Поэтому между контентом и архивом стоит офлайн-проверка.

Порядок: **правка → валидация → прогон на ВМ → упаковка → контрольная сумма → релиз**. Пропуск любого шага — причина откатывать изменения.

## 2. Инструменты (появятся на этапе v0.1)

Кода пока нет; здесь зафиксирован контракт.

### `tools/validate.py` — офлайн-валидатор

Проверяет без запуска AME:

| Проверка | Что ловит |
|---|---|
| Разбор `playbook.conf` | невалидный XML, отсутствие обязательных свойств, неверный формат `Version` и `UniqueId` |
| Уникальность | дубли `ID` действий и параметров, одинаковые имена опций |
| Лимиты FeaturePages | 4 чекбокса, 3 радио, `TopLine` ≤ 3, обязательные `IsRequired`/`DefaultOption` на радио |
| Совместимость с injection | динамические действия с `iso: true` / `only` — падение на разборе |
| Операции служб | `iso:` только для `delete` / `change` |
| Ссылочная целостность | `!task` указывает на существующий файл; `option` в YAML объявлен в `playbook.conf` |
| Гейты сборок | синтаксис `builds` корректен, нет противоречивых условий |
| Порядок фаз | числовые префиксы не дублируются, `00` идёт первой, отчёт — последним |
| Артефакты | наличие `playbook.png` (256 px), `Executables/` содержит обещанные сценарии |
| Запреты | наличие запрещённых тем из [SAFETY](SAFETY.md) в описаниях и действиях |

Код возврата: `0` — можно упаковывать, иначе — список ошибок с путями.

### `tools/package.py` — упаковщик

1. Проверяет результат валидатора.
2. Собирает архив формата 7z из **содержимого** `Playbook/` (не из папки целиком).
3. Имя: `Bare OS-<версия>.apbx`.
4. Считает SHA-256 архива, пишет рядом файл контрольной суммы.
5. Кладёт в `releases/`.

Требования к совместимости: архив обязан открываться AME, поэтому расширение `.apbx`, формат 7z и пароль `malte` — не косметика, а часть формата.

## 3. Версионирование

| Правило | Значение |
|---|---|
| Формат версии | как у AME: `0.1`, `0.0.1`; в проекте — `0.1`, `0.2`, `1.0` |
| `UniqueId` | не меняется никогда |
| Совместимость | минорная версия может менять состав; ломающие изменения — только с записью в `CHANGELOG` |
| Тег репозитория | совпадает с `Version` в `playbook.conf` |
| AME Wizard | версия, на которой тестировали, фиксируется в `CHANGELOG` и в `docs/` |

## 4. Чек-лист релиза

- [ ] Валидатор проходит без ошибок.
- [ ] Прогон на чистой ВМ 26H2 Pro выполнен, отчёт приложен.
- [ ] Верификатор: нет `mismatch`, все `unexpected change` объяснены.
- [ ] Тест отката пройден, сравнение с исходным состоянием сходится.
- [ ] Повторный прогон идемпотентен.
- [ ] `SupportedBuilds` содержит только реально прогнанные сборки.
- [ ] Каждое изменение имеет запись в [DECISIONS](DECISIONS.md), если оно спорное.
- [ ] `ProgressText` соответствует фактическим шагам.
- [ ] Список необратимого в отчёте совпадает с [REVERT](REVERT.md).
- [ ] SHA-256 посчитан и опубликован вместе с файлом.
- [ ] `CHANGELOG` заполнен: что добавлено, что убрано, что изменилось в поведении.

## 5. Артефакты релиза

| Файл | Назначение |
|---|---|
| `Bare OS-<версия>.apbx` | playbook для AME Wizard |
| `Bare OS-<версия>.apbx.sha256` | контрольная сумма |
| `REPORT-<версия>.html` | отчёт тестового прогона |
| `REVERT.md` (копия) | как откатывать: чтобы инструкция была рядом с файлом |

## 6. Воспроизводимость

1. База — оригинальный ISO Microsoft; его хеш фиксируется в отчёте прогона.
2. Версия AME Wizard фиксируется.
3. Версия playbook фиксируется.
4. Конфигурация тестовой ВМ (объём диска, число ядер, режим прошивки) фиксируется.

Без этих четырёх пунктов «у меня работает» не воспроизводится и, значит, не считается результатом.

## 7. Публикация (после v1.0)

1. Свой ключ подписи для хранения и проверки релизов.
2. Публичная страница с версией, контрольной суммой и известными ограничениями.
3. `ProductCode` запрашивается у AME только после прохождения матрицы целиком; до этого playbook помечается как непроверенный.
4. Политика: никаких «тихих» релизов — каждое изменение видно в `CHANGELOG`.

## 8. Откат релиза

Если релиз оказался дефектным:

1. Отозвать файл и контрольную сумму со страницы.
2. Выпустить версию с исправлением; не перезаписывать архив под тем же номером.
3. Запись в `CHANGELOG` с описанием дефекта и списком затронутых сборок.
