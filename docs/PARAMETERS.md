# Модель параметра и правила приёма

## 1. Почему не список «твиков»

Набор изменений — не плоский список строк YAML. Каждое изменение проходит одинаковый фильтр и описывается карточкой. Причины прагматичные:

1. Строка YAML не отвечает на вопрос «что сломается, если это включить».
2. Без карточки невозможно снять prior-state и построить откат.
3. Без критерия проверки невозможно понять, применилось ли изменение.
4. Без статуса невозможно отличить проверенное от «кто-то написал в интернете».

## 2. Карточка параметра

| Поле | Назначение |
|---|---|
| `ID` | стабильный идентификатор, например `privacy.diag.level` |
| `Категория` | реестр / службы / Appx / задачи / приватность / удобство / латентность |
| `Действие` | какой `!action` реализует |
| `Область` | машина / пользователь |
| `Цель и контекст` | точный ключ/ресурс, SID пользователя, 32/64-битное представление реестра, режим исполнения |
| `Источник и применимость` | URL, дата проверки, редакция, архитектура, build + UBR, версия AME |
| `Исходное и ожидаемое состояние` | способ чтения до изменения, ожидаемый результат и правило разрешения конфликта при откате |
| `Задержка` | требуется ли перезагрузка или перелогин |
| `Риск` | T0–T4 по [SAFETY](SAFETY.md) |
| `Обратимость` | что нужно, чтобы вернуть как было; отдельно фиксируется «необратимо» |
| `Гейт` | к какой `option` / FeaturePage привязан (если привязан) |
| `Обоснование` | зачем это нужно, без ссылок на «все так делают» |
| `Что ломает` | конкретные сценарии, которые перестают работать |
| `Проверка` | как верификатор подтверждает результат |
| `Критерий эффекта` | измеримое, если заявлен эффект на производительность |
| `Статус` | см. §3 |

## 3. Статусы

| Статус | Значение |
|---|---|
| `proposed` | заявлен, не проверен |
| `accepted` | включён в набор, но ещё не прогнан на 26H2 |
| `verified` | прогнан по [TEST-MATRIX](TEST-MATRIX.md), результат в отчёте |
| `rejected` | рассмотрен и отклонён, причина сохранена |

Правило: в релиз попадают только `verified`. `accepted` не блокирует отладку, но блокирует публикацию.

## 4. Уровни риска

| Tier | Описание | Требование |
|---|---|---|
| T0 | чтение, диагностика | — |
| T1 | обратимое, без перезагрузки | карточка + проверка |
| T2 | обратимое, с перезагрузкой или влиянием на поведение системы | карточка + проверка + запись в отчёте |
| T3 | влияет на безопасность или загрузку | отдельная опция, выключена по умолчанию, текст «что ломает» в описании |
| T4 | необратимо или разрушающе | не включается |

Риск и обратимость — разные поля. T3 не отменяет запреты [SAFETY](SAFETY.md): запрещённая операция не допускается через опцию. Для Appx различаются восстановление регистрации/пакета и возврат пользовательских данных. Кандидат может остаться T2 только при доказанном восстановлении затронутого состояния; без него это T4. Наличие приложения в Store само по себе не доказывает восстановимость.

## 5. Категории и их правила

| Категория | Плановый объём | Правила |
|---|---|---|
| Приватность и телеметрия | средний | только параметры, не ломающие Store, обновления и вход; ничего, что блокирует диагностику на уровне, нужном для античита |
| Потребительский мусор (Appx) | небольшой | только явный маркетинговый контент; Store, Xbox-стек, компоненты игр и разработки сохраняются ([DECISIONS](DECISIONS.md) D-007) |
| Удобство и оболочка | средний | обратимое, T1; не ломает Проводник и поиск |
| Службы | минимальный | только из allowlist, построенного по зависимостям ([SAFETY](SAFETY.md) §3) |
| Запланированные задачи | небольшой | только телеметрия и потребительские предложения; системные задачи обслуживания не трогаются; учитывается, что часть задач пересоздаётся компонентами |
| Латентность и планировщик | минимальный | только при наличии измеримого критерия и без вмешательства в драйверный слой |
| Инварианты разработчика | ноль изменений | проверяются, но не меняются: WSL2, Docker, Hyper-V, Store, Xbox, драйверы |

## 6. Шаблон таблицы параметров

Таблица заполняется по мере проектирования контента. Реальные ключи и значения вносятся на этапе v0.1, здесь фиксируются только идентификаторы и статусы.

| ID | Категория | Действие | Риск | Обратимость | Гейт | Статус |
|---|---|---|---|---|---|---|
| `privacy.diag.level` | приватность | `!registryValue` | T1 | да | — | proposed |
| `privacy.advertising.id` | приватность | `!registryValue` | T1 | да | — | proposed |
| `shell.taskbar.search` | оболочка | `!registryValue` | T1 | да | — | proposed |
| `appx.consumer.<name>` | Appx | `!appx` | T4 до доказательства восстановления | не доказана | требуется отдельное решение D-007 | proposed |
| `task.telemetry.<name>` | задачи | `!scheduledTask` | T2 | да, если сохранён экспорт | — | proposed |
| `service.<name>` | службы | `!service` | T2 | да, если снят prior-state | — | proposed |

Полный список с обоснованиями ведётся на этапе v0.1; до этого таблица выше — каркас.

## 7. Чек-лист приёма параметра

Изменение попадает в `Playbook/`, только если на все вопросы есть ответ:

1. Что именно меняется — действие, область, тип значения.
2. Зачем — обоснование без «так принято».
3. Что ломает — конкретные сценарии, а не «может повлиять».
4. Можно ли вернуть — и как именно.
5. Как проверить, что применилось — конкретная проверка, входящая в верификатор.
6. Нужен ли гейт — и если да, то выключен ли он по умолчанию.
7. Есть ли конфликт с инвариантами из [SAFETY](SAFETY.md).
8. Есть ли измеримый эффект, если он заявлен.
9. Запись в [DECISIONS](DECISIONS.md), если решение спорное.
10. Как влияет на время OOBE — не удлиняет ли первую загрузку непропорционально.
11. Какая версия источника подтверждает действие и где находится prior-state для выбранного режима.
12. Как определяется нужный пользователь: `HKCU` привилегированного процесса не считается профилем владельца.

## 8. Что заведомо не появится в наборе

- Отключение Defender, обновлений, Store, виртуализации и защиты памяти.
- Удаление и правка WinSxS, component store, BCD, WinRE.
- Вмешательство в Driver Store и файлы драйверов.
- Смена владельцев и ACL системных каталогов.
- «Мифические» оптимизации без критерия проверки: таймеры разрешения, режимы MSI, отключение файла подкачки и подобное — только при наличии измерения и понимания последствий.
- Одноразовые `!cmd`-однострочники вне `Executables/`.
