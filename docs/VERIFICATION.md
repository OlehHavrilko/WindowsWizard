# Верификация: контракт проверки после применения

## 1. Зачем отдельный контракт

Playbook может «выполниться успешно» и не изменить ничего. Два реальных механизма этого:

1. Windows игнорирует параметр — пример: политика отключения Defender при включённой Tamper Protection применяется молча и не действует.
2. Действие применено, но перекрыто более приоритетным источником — политика организации, MDM, значение, которое перезаписывает компонент.

Поэтому факт применения проверяется постусловиями, а не по отсутствию ошибок в логе.

## 2. Три артефакта

| Артефакт | Когда | Что делает |
|---|---|---|
| **Preflight-снимок** | первая фаза, до любых изменений | сохраняет prior-state по каждому планируемому параметру и состояние инвариантов |
| **Верификатор** | последняя фаза | сравнивает фактическое состояние с ожидаемым; ничего не меняет |
| **Отчёт** | последняя фаза, после верификатора | сводка: применено / не применено / изменено вне плана / необратимо |

Все три — часть `Playbook/Executables/`, вызываются как `!powerShell` на OOBE. Скрипты появятся на этапе v0.1; здесь фиксируется их контракт.

## 3. Что проверяется

### 3.1 Инварианты (блокирующие)

Не сохранение любого из них — провал прогона, даже если всё остальное применилось.

| Проверка | Ожидание |
|---|---|
| Загрузка и вход | система загрузилась, пользователь вошёл |
| Secure Boot | включён (или состояние совпадает с prior-state, если выключен был изначально) |
| TPM | присутствует, включён, версия 2.0 |
| VBS / Memory Integrity | состояние совпадает с prior-state |
| Гипервизор и `VirtualMachinePlatform` | присутствуют, состояние совпадает |
| WSL2 | подсистема работает, дистрибутивов не убавилось, служба в рабочем состоянии |
| Docker | служба/движок в рабочем состоянии (если был установлен до прогона) |
| Store | пакет на месте, запуск проходит |
| Xbox-стек | пакеты на месте |
| Windows Update | служба не отключена, проверка обновлений проходит |
| Драйверы | количество и состав пакетов не уменьшилось, ключи классов устройств сохранены |
| Defender | присутствует, состояние совпадает с prior-state |

### 3.2 Постусловия применённых параметров

По каждому принятому параметру — одна проверка, которая читает **фактическое** состояние и сравнивает с ожидаемым. Требования к проверке:

1. Различает «значение не задано» и «значение равно дефолту». Это разные состояния, и для отката важно именно первое.
2. Читает то место, откуда компонент действительно берёт настройку, а не то, куда мы писали. Если писали в политику — проверяется эффект политики, а не ключ.
3. Не зависит от языка интерфейса и локали.
4. Не требует интерактивного ввода.

### 3.3 Сверка с планом

| Категория | Значение |
|---|---|
| `applied` | ожидалось и подтверждено |
| `mismatch` | ожидалось, но фактическое состояние другое — ошибка прогона |
| `skipped` | не применялось по гейту (опция не выбрана, сборка не та) — норма |
| `unexpected change` | изменилось то, чего не было в плане — требует объяснения |
| `irreversible` | применено и не может быть возвращено — перечисляется явно |

## 4. Критерии приёмки прогона

1. Все инварианты сохранены.
2. Ни одного `mismatch`.
3. Все `unexpected change` объяснены (обычно это следствия, а не прямые изменения).
4. Список `irreversible` совпадает с тем, что было объявлено до применения.
5. Повторный запуск apply не даёт новых изменений и не даёт `mismatch`.
6. Повторный запуск verify после отката показывает исходное состояние.

## 5. Проверка идемпотентности

Отдельный сценарий: применение на уже применённую систему.

- Ожидание: все параметры в состоянии `applied`, отчёт не содержит изменений, время выполнения кратно меньше.
- Причина: на OOBE повторный прогон возможен (пользователь перезапустил установку, обновил версию playbook), и он не должен ничего ломать.

## 6. Проверка остатков «управляется организацией»

Признак проблемы: мы писали в канал политик, а пользователь не может изменить настройку.

Проверяется:

1. Наличие параметров политик, которых нет в плане прогона.
2. Признаки внешнего управления: домен, MDM-регистрация, сторонний EDR.
3. Текст уведомления о политике в интерфейсе — применительно к тем разделам, которые мы трогали.

Следствие: если внешнее управление обнаружено, playbook не «перебивает» его, а сообщает о конфликте в отчёте.

## 7. Формат результата

| Вывод | Содержание |
|---|---|
| консоль | краткая сводка: сколько проверок, сколько провалов, код возврата |
| JSON рядом с отчётом | машиночитаемые результаты по каждой проверке: ID, ожидание, факт, вердикт |
| HTML | человекочитаемый отчёт: по категориям, с выделением необратимого и провалов |

Правило: отчёт обязан быть понятен человеку, который не писал playbook, и обязан содержать путь к preflight-снимку.

## 8. Чего верификатор не делает

- Не исправляет найденные расхождения.
- Не откатывает изменения.
- Не заменяет тестирование на ВМ.
- Не проверяет то, что проверить нельзя без игрового процесса (реальный frametime), — только заявленные настройки и доступность компонентов.
