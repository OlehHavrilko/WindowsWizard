# Действия (`actions`) — доступный инструментарий

Список действий сверен по документации AME. Точные наборы параметров каждого действия — в разделах `developers/actions/<Name>` официальной документации; здесь зафиксированы назначение, совместимость с этапами и правила применения в этом проекте.

## 1. Полный перечень

| Действие | Назначение | Injection | Приоритет в проекте |
|---|---|---|---|
| `!registryValue` | записать/изменить значение реестра | да | основной инструмент |
| `!registryKey` | создать/удалить ключ реестра | да | используется редко, только вместе со значением |
| `!service` | правка типа запуска, удаление службы | только `delete` / `change` | ключевой инструмент для offline-этапа |
| `!appx` | удаление Appx, очистка кэшей | **нет** | только OOBE |
| `!scheduledTask` | удаление/правка запланированных задач | **нет** | только OOBE |
| `!systemPackage` | удаление компонентов Windows | **нет** | в v0.1 не используется |
| `!file` | файловые операции | да | минимально |
| `!download` | скачивание ресурса в образ | да (по умолчанию) | кэш для OOBE |
| `!software` | установка ПО из источника (например chocolatey) | да (по умолчанию) | по необходимости |
| `!task` | подключение файла задач | да (по умолчанию) | каркас `main.yml` |
| `!status` / `!writeStatus` | сообщение на экране прогресса | — | обязательная разметка фаз |
| `!cmd` | команда cmd | **нет** | только OOBE, минимум |
| `!powerShell` | команда PowerShell | **нет** | только верификатор и отчёт |
| `!run` | запуск исполняемого файла | **нет** | только для собственных утилит из `Executables/` |
| `!taskKill` | завершение процесса | **нет** | только при обоснованной необходимости |

## 2. Совместимость с этапами

Три состояния совместимости:

- **да** — выполняется штатно;
- **нет** — разбор playbook падает целиком, а не пропускает действие;
- **частично** — зависит от операции.

| Действие | `iso:` | `oobe:` | Комментарий |
|---|---|---|---|
| `!registryValue`, `!registryKey` | да | да | единственный класс изменений, который надёжно ложится офлайн |
| `!file` | да | да | путь считается от образа при injection |
| `!download`, `!software` | да (дефолт) | да | при injection кэшируется, на OOBE ставится из кэша |
| `!task` | да (дефолт) | да | вложенный файл исполняется по правилам своих действий |
| `!service` | частично | да | injection только для `delete` и `change` |
| `!appx`, `!systemPackage`, `!cmd`, `!powerShell`, `!run`, `!taskKill` | нет | да | динамические действия запрещены при injection |

Практическое правило: если действие нельзя выполнить на injection, оно идёт в OOBE — и его нужно делать быстрым и идемпотентным, потому что это первая загрузка свежей системы.

## 3. Общие свойства всех действий

| Свойство | Значение |
|---|---|
| `option` | выполнять только если выбрана опция с этим именем |
| `options` | выполнять при любой из перечисленных опций |
| `option` с `!` | инверсия: выполнять, если опция **не** выбрана |
| `builds` | гейт по сборке: `['26300']`, `['>=26100']`, `['>=26100','!>26200']`, `['22621.1265']` |
| `iso` | `true` / `false` / `only` |
| `oobe` | `true` / `false` / `only` |

`builds` поддерживает `>=`, `<=`, `>`, `<`, отрицание (`!>`) и номер UBR. Гейты читаются по-разному: при injection — по образу, который собирается, при обычном прогоне — по работающей системе.

## 4. Правила применения в проекте

1. **Реестр — только парами «ключ + значение»** с явным типом (`REG_DWORD`, `REG_SZ`, `REG_BINARY`). Тип обязателен: неверный тип — молча неработающая настройка.
2. **Службы — только из allowlist.** Ни одна служба не меняется, пока не проверены её критичность для загрузки, граф зависимостей и наличие потребителей. См. [SAFETY](SAFETY.md).
3. **`!appx` — только для потребительского мусора.** Удаление необратимо: вернуть можно только через Store или обновление Windows. Правило: если приложение упоминается в инструкции к игре, драйверу или средству разработки — не трогать.
4. **`!systemPackage` — не используется в v0.1.** Самый необратимый слой; вводится по одному компоненту, отдельным релизом и отдельным прогоном.
5. **`!powerShell` / `!cmd` / `!run` — только для собственных артефактов** из `Executables/`: верификатор, отчёт, откат. Никаких однострочников с исправлениями «по месту»: они не проходят валидацию и не попадают в отчёт.
6. **`!taskKill` — только с обоснованием** в [DECISIONS](DECISIONS.md). Завершение процесса ради того, чтобы удалить пакет, — не повод.
7. **`!writeStatus` между фазами обязателен.** Пользователь должен видеть, на каком шаге что-то пошло не так; без этого отладка на чужой машине невозможна.
8. **`!download` / `!software` — на injection**, чтобы OOBE не зависел от сети. Это и есть штатная рекомендация платформы.

## 5. Чего в наборе действий нет и что это значит

| Задача | Как решается |
|---|---|
| «прочитать» значение реестра перед записью | средствами платформы напрямую нельзя; снимается собственным сценарием в `00-preflight.yml` (это `!powerShell`, значит только OOBE) |
| условная логика «если — то» | только через `option` / `builds` / отдельные сценарии; декларативной логики нет |
| транзакционность (всё или ничего) | отсутствует: частично применённый playbook — нормальное состояние, поэтому откат обязателен |
| откат | отсутствует как механизм; реализуется отдельным артефактом ([REVERT](REVERT.md)) |
| проверка результата | отдельным сценарием внутри playbook ([VERIFICATION](VERIFICATION.md)) |

Отсутствие условной логики — главное ограничение при проектировании: если параметр зависит от состояния системы (например, от наличия конкретного драйвера), это решается не в YAML, а в проверочном сценарии, который сообщает о несовместимости, а не пытается её обойти.


## 6. Действия движка `feature` и `cleanup` (D-035)

Это действия карточек каталога `catalog/*.yml`, а не AME-действия из разделов выше.

| Действие | YAML | Что делает | verify | revert |
|---|---|---|---|---|
| `feature` | `feature: { name: Recall, state: Disabled }` (`Enabled` или `Disabled`) | отключает или включает необязательный компонент Windows через `dism.exe` (`/Get-FeatureInfo /English`, `/Disable-Feature /NoRestart`, `/Enable-Feature /All /NoRestart`); код 3010 (нужна перезагрузка) не ошибка | состояние совпадает с ожидаемым; компонента нет в сборке (`<absent>`) для `Disabled` считается выполненным | возвращает исходное состояние из baseline |
| `cleanup` | `cleanup: { kind: ComponentStore }` или `{ kind: Temp }` | одноразовая очистка: `ComponentStore` — `dism /Online /Cleanup-Image /StartComponentCleanup` (без `/ResetBase`); `Temp` — содержимое `%WINDIR%\Temp` и `%TEMP%` (занятые файлы пропускаются молча) | всегда `Verified`; повторный apply допустим | ничего не делает, статус `Skipped` (необратимо) |

Правила:

1. Имя компонента — только `[A-Za-z0-9._-]`, 3–128 символов. Загрузчик каталога отклоняет Hyper-V, `VirtualMachinePlatform`, `HypervisorPlatform`, `Microsoft-Windows-Subsystem-Linux`, `Containers`, `Windows-Defender` (подстрока, без учёта регистра).
2. `cleanup` замеряет свободное место на системном диске до и после: в отчёте `Before = free=<байт>`, `After = free=<байт>`; разница — освобождённые байты для Proof Report.
3. Обычно после `feature` нужна перезагрузка; в отчёте это не ошибка.
