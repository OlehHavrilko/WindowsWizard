# Дорожная карта

Правило: этап считается закрытым только при выполнении критериев выхода. Сроки не фиксируются — фиксируется состав работ, потому что блокирующим фактором является количество прогонов на 26H2, а не календарь.

## v0.0 — документация и структура (выполнено)

**Состав:** README, архитектура, справочник `playbook.conf`, справочник действий, журнал решений, модель параметра, безопасность, верификация, откат, сборка, тест-матрица, риски; каркас каталогов.

**Критерий выхода:** документы согласованы между собой, решения зафиксированы, противоречий нет.

**Чего нет:** ни одной строки YAML, ни одного скрипта, ни одного реального параметра.

## v0.1 — каркас и первый рабочий прогон

**Состав:**
1. `playbook.conf` с корректными метаданными, `SupportedBuilds`, двумя требованиями.
2. `main.yml` с фазами `00`…`90` и `!writeStatus`.
3. Контент только в двух слоях: реестр и службы (узкий allowlist).
4. `Executables/`: preflight-снимок, верификатор, отчёт.
5. `tools/`: валидатор и упаковщик.
6. Первый `.apbx` + SHA-256.

**Критерии выхода:**
- прогон S-01 на чистой 26H2 Pro проходит;
- верификатор не даёт `mismatch`;
- playbook применяется дважды без изменений (S-02);
- валидатор проходит без ошибок;
- минимальный обратимый откат работает на доказанных обратимых целях (S-03), baseline не перезаписывается (S-13), сбой preflight останавливает изменения (S-11);
- отчёт и снимок лежат в `%ProgramData%\WindowsWizard\runs\<run_id>\` (S-15).

**Не входит:** Appx, задачи, FeaturePages, ISO, необратимые цели.

Откат не откладывается на v0.2: без него нельзя доказать ни одну обратимую настройку (см. [REVIEW](REVIEW.md)).

## v0.2 — обратимость и потребительский слой

**Состав:**
1. Сценарий отката по prior-state.
2. Удаление мусорных Appx.
3. Запланированные задачи: телеметрия и потребительские предложения.
4. Приватность.
5. HTML-отчёт с перечнем необратимого.

**Критерии выхода:**
- S-03 и S-04 проходят, сравнение с исходным состоянием сходится с точностью до объяснённого;
- отчёт читается человеком, не писавшим playbook;
- инварианты разработчика (WSL2, Docker, Store, Xbox) подтверждены на прогоне.

## v0.3 — ISO-путь

**Состав:**
1. `SupportsISO`, `<OOBE>` с тремя `BulletPoint`, `<ISO><DisableBitLocker>`.
2. Раскладка действий по `iso:` / `oobe:`: реестр и правка служб — offline, приложения и задачи — OOBE.
3. Кэширование загрузок через `!download` / `!software`.
4. Прогон S-05: сборка ISO → установка с носителя → OOBE.

**Критерии выхода:**
- установка с собранного ISO проходит, playbook применяется на первом запуске;
- OOBE не требует сети для своих действий;
- сборка ISO не падает на разборе действий;
- шифрование диска на этапе setup не включается.

**Риск этапа:** второй этап исполнения (OOBE) ранее не проверялся, а первый запуск свежей системы — самое шумное место.

## v0.4 — опции и профили

**Состав:**
1. FeaturePages с лимитами и дефолтами (рискованное — выключено).
2. Гейты `option` в YAML, включая инверсию.

- описания опций говорят, что ломается, без обтекаемых формулировок.

## v0.5 — наведение порядка в контенте

**Состав:**

**После v1.0 (опционально):** подпись релизов, публичная страница, `ProductCode` после ревью AME, публикация исходников через `Git`.

## Зависимости этапов

```
v0.0 → v0.1 → v0.2 → v0.3 → v0.4 → v0.5 → v1.0
              └──────────────────────────┘
        (откат и верификатор блокируют все последующие этапы)
```

Откат и верификатор вводятся в v0.1–v0.2 и далее не переделываются: любой этап, добавляющий изменения, обязан сразу их учитывать в обоих артефактах. Нарушение этого правила — причина, по которой проекты такого класса разваливаются.
