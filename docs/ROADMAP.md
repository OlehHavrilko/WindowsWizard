# Дорожная карта

Правило: этап считается закрытым только при выполнении критериев выхода. Сроки не фиксируются — фиксируется состав работ, потому что блокирующим фактором является количество прогонов на 26H2, а не календарь.

## Функции-отличия по этапам

Функции F-01…F-10 из [DIFFERENTIATORS](DIFFERENTIATORS.md) распределены по этапам ниже и не меняют критериев выхода, пока не приняты D-014 и D-015 ([DECISIONS](DECISIONS.md)).

| Этап | Функции |
|---|---|
| v0.1 | F-04 Plan / Dry-run, F-01 Proof Report (текст), F-02 минимальный откат, F-09 валидатор в CI |
| v0.2 | F-01 HTML, F-02 полный откат, F-05 Drift Guard, F-06 базовые замеры, F-07 инварианты, F-03 формат карточек |
| v0.4 | F-07 Compat Contract полностью, F-08 план под железо |
| v0.5 | F-03 генерация из карточек, F-06 frametime |
| после v0.5 | F-10 линия Lab — по одной опции отдельным релизом |
| v1.0 | F-09 публикация результатов матрицы, подпись релизов |

Порядок работ — D-023: сначала движок (v0.1), затем playbook как обёртка (v0.2), затем ISO-путь и опции. Устройство — [ARCHITECTURE](ARCHITECTURE.md) §3–5.

Toolbox ведётся отдельной линией T-v0.1…T-v0.4 ([TOOLBOX](TOOLBOX.md) §7) и начинается после закрытия v0.2: к этому моменту API движка стабилен.

## v0.0 — документация и структура (выполнено)

**Состав:** README, архитектура, справочник `playbook.conf`, справочник действий, журнал решений, модель параметра, безопасность, верификация, откат, сборка, тест-матрица, риски; каркас каталогов.

**Критерий выхода:** документы согласованы между собой, решения зафиксированы, противоречий нет.

**Чего нет:** ни одной строки YAML, ни одного скрипта, ни одного реального параметра.

## v0.1 — движок

**Состав:**
1. Решение `src/`: `BareOS.Core` (библиотека), `BareOS.Cli` (`bareos.exe`), `BareOS.Core.Tests`. .NET 10, D-027.
2. Формат карточки в YAML по [PARAMETERS](PARAMETERS.md) §2 и схема для валидации; каталог `catalog/`.
3. Команды `plan`, `apply`, `verify`, `revert`, `report` (текст) — [ARCHITECTURE](ARCHITECTURE.md) §4.1.
4. Обработчики `registry`, `service`, `task`.
5. Снимок, журнал, блокировка параллельного прогона, хранение в `%ProgramData%\BareOS\runs\<run_id>\`.
6. Первые 10–15 карточек класса A (официальные политики) из пресета «ядро» по [TWEAKS-BASELINE](TWEAKS-BASELINE.md).
7. CI на `windows-latest`: сборка, модульные тесты, валидация каталога.

**Критерии выхода:**
- `apply` на чистой 26H2 Pro (ВМ) проходит, `verify` не даёт `mismatch` (S-01);
- повторный `apply` ничего не меняет (S-02);
- `revert` возвращает снимок, baseline не перезаписывается (S-03, S-13);
- сбой preflight даёт код 2 и ни одного изменения (S-11);
- отчёт и снимок лежат в `%ProgramData%\BareOS\runs\<run_id>\` с правильными правами (S-15).

**Не входит:** AME, Appx, GUI, ISO, необратимые цели.

## v0.2 — playbook-обёртка и потребительский слой

**Состав:**
1. `playbook.conf` (Name `Bare OS`, `SupportedBuilds` на семейство `>=26100`), `main.yml` с фазами `00`…`90` ([ARCHITECTURE](ARCHITECTURE.md) §5).
2. `tools/`: валидатор и упаковщик, первый `Bare OS-<версия>.apbx` + SHA-256.
3. Обработчик `appx`; карточки Appx, задач телеметрии, приватности; пресет «Стандарт» (Copilot, Recall, Edge — D-017).
4. HTML-отчёт с перечнем необратимого.

**Критерии выхода:**
- live-прогон через AME Wizard проходит S-01, S-02, S-11 (остановка AME по коду возврата доказана);
- S-03 и S-04 проходят, сравнение с исходным состоянием сходится с точностью до объяснённого;
- инварианты (WSL2, Docker, Store, Xbox, Defender, Windows Update) подтверждены на прогоне.

## v0.3 — ISO-путь

**Состав:**
1. `SupportsISO`, `<OOBE>` с тремя `BulletPoint`, `<ISO><DisableBitLocker>`.
2. Движок на OOBE: снимок живой системы до изменений; пользовательские цели — через Default User или после первого входа ([EXECUTION-CONTRACT](EXECUTION-CONTRACT.md) §3).
3. Кэширование загрузок через `!download` / `!software`.
4. Прогон S-05: сборка ISO → установка с носителя → OOBE.

**Критерии выхода:**
- установка с собранного ISO проходит, движок отрабатывает на первом запуске;
- OOBE не требует сети для своих действий;
- шифрование диска на этапе setup не включается.

**Риск этапа:** первый запуск свежей системы — самое шумное место; пользовательский профиль на OOBE ещё не существует.

## v0.4 — опции и профили

**Состав:**
1. FeaturePages с лимитами и дефолтами (рискованное — выключено); выбор передаётся движку как опции.
2. Опции и пресеты в карточках; гейты `option` в YAML только для фаз playbook.
3. Профили: минимальный набор страниц под сценарии (игры / разработка).
4. `EstimatedMinutes`, `ProgressText` с реальными шагами.

**Критерии выхода:**
- каждая комбинация опций, объявленная в релизе, имеет прогон;
- ни одна рискованная опция не включена по умолчанию;
- описания опций говорят, что ломается, без обтекаемых формулировок.

## v0.5 — наведение порядка в контенте

**Состав:**
1. Ревизия каждого параметра: статус `verified` или удаление.
2. Сведение дублей и конфликтующих настроек.
3. Проверка на повторяемость после обновления Windows (S-09); самопроверка `verify` после обновления ([ARCHITECTURE](ARCHITECTURE.md) §6).
4. Решение по `!systemPackage` (Q-04): включать или закрыть вопрос.

**Критерии выхода:**
- в наборе нет параметров со статусом ниже `verified`;
- каждое изменение имеет измеримое или иное явное обоснование.

## v1.0 — приёмка

**Состав:**
1. Прогон полной матрицы, включая физическую машину.
2. Фиксация версии AME Wizard и хеша базового ISO.
3. Релизные артефакты и инструкция по откату рядом с файлом.

**Критерии выхода:**
- все сценарии S-01…S-10 пройдены;
- откат проверен на чистой ВМ;
- документация соответствует фактическому поведению playbook.

**После v1.0 (опционально):** подпись релизов, публичная страница, `ProductCode` после ревью AME, публикация исходников через `Git`.

## Зависимости этапов

```
v0.0 → v0.1 → v0.2 → v0.3 → v0.4 → v0.5 → v1.0
              └──────────────────────────┘
        (откат и верификатор блокируют все последующие этапы)
```

Откат и верификатор вводятся в v0.1–v0.2 и далее не переделываются: любой этап, добавляющий изменения, обязан сразу их учитывать в обоих артефактах. Нарушение этого правила — причина, по которой проекты такого класса разваливаются.
